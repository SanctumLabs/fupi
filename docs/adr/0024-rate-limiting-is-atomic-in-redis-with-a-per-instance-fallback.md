# Rate limiting is counted atomically in Redis with a per-instance in-memory fallback, runs after auth and before idempotency, and takes the client IP from the rightmost untrusted address

**Four route groups, each with its own budget.** `auth` (any method under `/api/v1/fupi/auth/`) and `redirect` (`GET` on a code-shaped path, `^/[a-zA-Z0-9-]{3,12}$`) and `default` (everything else) are keyed by client IP; `create` (`POST /api/v1/fupi/urls`) is keyed by the authenticated user ID, and falls back to the IP when there is none. Keys are namespaced by group (`auth:ip:203.0.113.7`, `create:user:<id>`), so groups never share a bucket. An IPv6 client is keyed by its /64 (`auth:ip:2001:db8:1:2::/64`), not its full address: a host is usually handed a whole /64 and could otherwise take a fresh bucket for each of its addresses. IPv4 addresses are keyed one by one. `/health`, `/health/ready`, `/docs` and the prefix `/docs/` are never limited, so a probe cannot be answered with a 429 and an orchestrator cannot drain a healthy instance. The prefix is `/docs/`, not `/docs`: `/docs0000` is a valid short code. Groups are matched on the path as Fiber routes it (lower case, trailing slashes trimmed), so a request cannot move to a looser group by changing the case of its path or adding a slash. Each group's max and window, and the whole limiter, are set by `RATE_LIMIT_*` variables ([Architecture](../Architecture.md#rate-limiting)).

**Counted in Redis with GCRA, atomically.** The check is one Lua call per request through `redis_rate` on the go-redis client the cache already uses, so two API instances sharing Redis enforce one count. `gofiber/storage`, the usual way to give Fiber's limiter a shared store, is not used: its `Storage` interface is get and set, and a read followed by a write cannot be atomic, so concurrent requests would each see room and all get through.

**A steady rate with a burst, not a cap per window.** `max` per `window` means a client can spend `max` requests at once and then earns one back every `window/max`: with the `auth` defaults, 10 at once and then one every 6 seconds. There are no clock windows. Any span of one window can let through up to about `2×max − 1`: the burst plus a window's refill. For login the slow refill is the brake that matters, and a patient client is held to the steady rate. A limited request gets `429`, `Retry-After`, the `X-RateLimit-*` headers and `{"message":"too many requests"}`.

**Redis stays optional (ADR-0015).** Each Redis call is bounded by `RATE_LIMIT_REDIS_TIMEOUT_MS` (50 ms) through the request context. On any error the request is decided by Fiber's in-memory fixed-window limiter, built once per group, and the limiter stops asking Redis for `RATE_LIMIT_REDIS_RETRY_AFTER` seconds (5); after that one request at a time probes Redis while the others stay in memory, so a Redis that is still down costs one request the timeout, not all of them. A successful probe switches back; a failed one starts the cooldown again. A Redis error never fails a request and never lets one through unlimited. A success from a request that started before the cooldown ended is ignored, because it was in flight beside the failure; a slow Redis would otherwise flap between the two backends. Without a Redis client at all the limiter runs in memory from the start.

**The fallback is per instance.** With N instances sharing a limit, each counts on its own during an outage, so up to N× the limit gets through until Redis is back. This is accepted: limits are configurable, and the alternative, refusing requests while Redis is down, would make an optional dependency required. The signals are the gauge `http.ratelimit.fallback.active` (1 while in fallback), the counter `http.ratelimit.backend.errors` and two log lines, one `Warn` on switching (`rate limiter falling back to memory`, with the error) and one `Info` on switching back (`rate limiter back on redis`). Neither logs per request. `http.ratelimit.requests` carries `group`, `outcome` and `backend`; client IPs and user IDs are never metric attributes. They are on the request span (`ratelimit.key`), where unbounded values cost nothing.

**After authentication, before idempotency.** `server.NewServer` installs the guards, auth and then the limiter, after Helmet and Recover and before the idempotency middleware. The limiter runs after auth so `create` can key on the user ID. It runs before idempotency because Fiber's idempotency middleware stores whatever the chain answers for 30 minutes: a rate-limited `POST` carrying `X-Idempotency-Key` would replay its 429 for 30 minutes, ignoring `Retry-After`. Recover sits ahead of the guards, so a panic in auth or the limiter becomes a 500 and does not crash the process. The price of this order is that a missing or invalid token on a protected route is rejected with 401 before it reaches the limiter. That is acceptable: verifying a JWT is cheap, and the expensive endpoints (register, login, token) are public and so are limited.

**The client IP is the rightmost untrusted address, not Fiber's `ProxyHeader`.** For `X-Forwarded-For` Fiber returns the leftmost entry, which the client writes, so a client could send a new value on every request and get a fresh bucket each time. `SERVER_PROXY_HEADER` names the header and `SERVER_TRUSTED_PROXIES` lists the proxies (IPs or CIDRs). The header is read only when the connection's peer is a trusted proxy; the entries are then walked from the right and the first one that is not a trusted proxy is the client. Repeated header lines are read as one comma-separated list, in order (RFC 9110): a proxy that adds its own line after the client's would otherwise leave the client's line in charge. An entry that is not an IP, or a header with nothing usable, yields the peer address. The loader refuses a header without trusted proxies. With neither set the key is the connection's address. Nothing in this depends on a hosting provider.

## Considered options

- **`gofiber/storage` with Fiber's limiter** — the smallest change, but the store cannot count atomically across instances.
- **A fixed window in Redis (`INCR` plus `EXPIRE`)** — a hard cap per window, but it needs two commands or our own Lua, and it lets a client spend two windows' worth across a boundary. GCRA is one call that already exists in `redis_rate`.
- **Failing closed when Redis is down** — exact limits, but an optional dependency would take the API with it (ADR-0015).
- **Limiting before auth** — simpler wiring, but `create` could not be keyed by user and invalid tokens would consume the IP budget.

## Consequences

- During a Redis outage the effective limit is up to N× per instance count, and the in-memory buckets reset when an instance restarts.
- A limit is a rate, not a window cap, so a client can briefly send up to about `2×max − 1` in one window. Tune `max` and `window` with that in mind.
- The go-redis client now sets `ContextTimeoutEnabled`. Without it go-redis ignores a context deadline and waits for its own multi-second read timeout, so the 50 ms bound was not applied and a hung Redis stalled requests for about 3 seconds. The setting applies to every command on the shared client, including the redirect cache, so a deadline passed anywhere is now honoured.
- Limits are per client address or user, not per account: distributed credential stuffing against one account from many IPs is not caught. Per-plan quotas, allowlists and ban lists are not part of this.
- With `RATE_LIMIT_ENABLED=false` the limiter is not registered at all. Behind a proxy, leaving `SERVER_PROXY_HEADER` and `SERVER_TRUSTED_PROXIES` unset puts every client in the proxy's bucket.
- Load tests run through the limiter, so the load-test stack must raise the limits by environment variable; otherwise throughput runs are throttled.
