# The OpenAPI spec is generated from the handler annotations as Swagger 2.0 and embedded in the binary

The spec used to be a hand-edited `swagger.json` that described pre-v2 endpoints, while the v2 server served no docs at all. It is now generated by [swaggo/swag](https://github.com/swaggo/swag) from the `@Router`, `@Param`, `@Success` and `@Failure` annotations on the handlers (`app/api/v1/...`, `app/api/probes`) and the general info on `main()` in `app/cmd/main.go`. `make generate.open.api.docs` writes `app/api/openapi/swagger.json`; nothing in that file is edited by hand.

The file is embedded with `//go:embed` (`app/api/openapi`) and served by the server at `GET /docs/`, with the document itself at `/docs/swagger.json`. The distroless image (ADR-0016) has no working directory to read a spec from, and the server can no longer start without its docs. The docs are registered before the auth middleware, so they are public.

CI runs `make check.open.api.docs`, which regenerates the spec and fails on `git diff`, so a handler change without a regenerated spec fails the build.

swag runs through `go run github.com/swaggo/swag/cmd/swag@v1.16.4`, so the tool is pinned in the Makefile and is not a dependency in `go.mod`.

The spec declares no `@BasePath` and every `@Router` carries its full path (`/api/v1/fupi/urls`). The probes (`/health`) and the short-url redirect (`/{code}`) are served at the root, outside `/api/v1/fupi`, and Swagger 2.0 has a single `basePath` for every path.

Authentication is one scheme, `BearerAuth`, an `apiKey` in the `Authorization` header holding `Bearer <access token>`. Every `/urls` operation declares it; register, login, token refresh, verify, the probes and the redirect are public and declare none.

## Considered options

- **swag v2 (OpenAPI 3)** — gives `oneOf`, nullable types and better client generators, but it is a separate major version of the tool with its own annotation behaviour to adopt. None of the API's types needs those features yet.
- **Spec-first with `oapi-codegen`** — makes the spec the contract, but it would rewrite every handler and DTO the Fiber API already has. That is a much larger change than the problem (a spec that drifts) calls for.
- **Keeping the hand-written file** — it had already drifted away from the code.

## Consequences

- The spec is Swagger 2.0. Moving to OpenAPI 3 later means changing the generator and, if needed, annotations; the embed and the CI check stay.
- Swagger 2.0 has no real `bearer` scheme, so the "Authorize" box takes the full `Bearer <token>` value.
- Request and response shapes come from the DTO structs, so the annotations must name the right DTO. A wrong annotation compiles and generates a wrong spec; the route list is the thing the CI check can catch, not the annotation's accuracy.
- A new route needs annotations, or it is missing from the spec.
